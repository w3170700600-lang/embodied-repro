## 一、服务端现状（已就绪，不用动）

| 项 | 值 |
|---|---|
| 机器 | 8×RTX3090，`<SERVER_IP>:<SSH_PORT>`（`<user>`） |
| 目录 | `/home/ei/pi05` |
| checkpoint | `outputs/pi05_train8/checkpoints/004500/pretrained_model`（评测最优，MAE 0.3550） |
| 服务脚本 | `serve_http.py`，监听 `0.0.0.0:8000` |
| 返回步数 | **40 步**（≈1.33 s @30Hz） |
| 多采样 | **--samples 4**：同一输入跑 4 次取均值，压掉 flow matching 采样噪声 |
| 单次推理 | **约 580~630 ms**（40 步 + 4 采样，仍有余量 0.7 s） |
| 健康检查 | `GET /health` → `{"ok": true, "n_action_steps": 40, "samples": 4}` |

> **为什么加多采样**：单次采样时，同一张图连续请求 4 次，首步动作就差 3.5~4.6°、
> 整块最大差 83°，机械臂等于在随机抖动。4 采样取均值后，首步差降到 0.75~3.1°、
> 整块 2.8~4.1°。实测服务端耗时 580~630 ms，仍在 1.33 s 动作块内。

服务如果挂了，重启命令：

```bash
cd /home/ei/pi05
.venv/bin/python serve_http.py \
  --ckpt outputs/pi05_train8/checkpoints/004500/pretrained_model \
  --port 8000 --n 40
```

**注意**：云安全组没有放行 8000，所以外网直连不通（已验证）。必须走下面的隧道方案。

## 二、网络：SSH 隧道（推荐，不用改安全组）

在**接机械臂的那台机器**上开一个终端，挂隧道：

```bash
ssh -N -L 8000:127.0.0.1:8000 -p <SSH_PORT> <user>@<SERVER_IP>
```

这个窗口会一直挂着不返回，属于正常现象。保持它开着。

验证（另开一个终端）：

```bash
curl http://127.0.0.1:8000/health
# 期望: {"ok": true, "n_action_steps": 40}
```

> 如果提示 `Permission denied (publickey)`，说明这台机器没有授权密钥。
> 备选：去腾讯云控制台把安全组 8000 端口对你这台机器的出口 IP 放行，然后
> 把下面的 `--server` 换成 `http://<SERVER_IP>:8000`。

## 三、机器人端（在接机械臂的机器上）

### 3.1 环境要求

- 已装 `lerobot`（含 `feetech`，能驱动 SO-101）——你录数据用的那个环境就是对的
- `opencv-python`、`numpy`（lerobot 一般自带）
- 拿到 `robot_client.py`（同一个工作区里）

### 3.2 先空跑，不接机械臂（30 秒）

```bash
python robot_client.py --server http://127.0.0.1:8000 --dry-run
```

期望输出三行 `返回 40 步 ... 服务端 810ms ...`。这一步通了说明隧道和服务都没问题，
接机械臂之前就能确认，不用碰硬件。

### 3.3 真机

```bash
python robot_client.py \
  --server http://127.0.0.1:8000 \
  --port /dev/ttyACM0 \
  --robot-id my_follower \
  --camera 0 \
  --task "Grab the green cube" \
  --fps 30 \
  --max-step-deg 6 \
  --seconds 60
```

Windows 上串口名是 `COM3` 这类，`--camera 0` 是 opencv 的相机序号。

**首次务必这样跑**：
1. 手放在电源/急停上
2. `--seconds 15` 先跑一小段
3. 确认动作方向对、幅度合理，再放开时间

### 3.4 参数含义

| 参数 | 作用 | 建议 |
|---|---|---|
| `--max-step-deg` | 单周期内允许的最大关节变化 | 首跑 **6**，稳了再放到 10~15 |
| `--speed` | 时间缩放，<1 更慢 | 首跑可 `--speed 0.7` |
| `--fps` | 执行频率 | 保持 30（训练就是这个 fps） |
| `--task` | 语言指令 | **必须和训练时完全一致**：`Grab the green cube` |

**任务描述不能改**。模型是在这一条指令上微调的，换说法等于换了一个没见过的输入。

### 3.5 跑起来之后看什么

每 60 步会打一行：

```
执行 60 步 | 队列 12 | 推理均值 812ms | 失败 0 | 图 observation.images.front
```

| 指标 | 正常 | 异常含义 |
|---|---|---|
| 队列 | 8~30 之间波动 | 持续为 0 = 推理跟不上，机器人会顿；持续 >35 = 动作没被执行 |
| 推理均值 | 800~900 ms | 突然 >2000 ms = 服务端在抢卡或网络抖动 |
| 失败 | 0 | 出现即查隧道/服务 |

## 四、出问题先查这几条

| 现象 | 原因 | 处理 |
|---|---|---|
| `Connection refused` | 隧道断了 | 重开隧道窗口，`curl /health` 验证 |
| `Permission denied (publickey)` | 这台机器没密钥 | 换安全组直连方案 |
| `观测里找不到 shoulder_pan.pos` | lerobot 版本键名不同 | 把报错里的 `keys=` 发我，我改映射 |
| `观测里没有图像` | 相机没配 | 检查 `--camera`，或先用 `lerobot-find-cameras` |
| 机器人不动，队列一直满 | send_action 键名不匹配 | 看是否 `shoulder_pan.pos` vs `shoulder_pan` |
| 动作猛跳 / 抖动 | 模型输出越界 | 降低 `--max-step-deg` 到 3~4，或 `--speed 0.5` |
| 抓到一半松手 | 夹爪动作滞后 | 已知问题（数据里 action/state 夹爪差 26% 帧），先观察 |

## 五、对这版模型的合理预期

评测在 5 条 holdout 上：MAE 0.3550，比"保持不动"基线好 **24.8%**。这是**离线指标**，
不等于成功率。以下因素会拉低真机表现：

- **单相机、物体只占画面 4.4%**（28×26 px，缩到 224 只剩 10 px）
- **34/56 条起点几乎相同**，模型学到的主要是"从这一个位置抓"
- **夹爪在抓取相位被自身遮挡**（相机和机械臂同侧）
- 方块位置一旦明显偏离训练分布，成功率会断崖

所以真机上建议：**先把方块放回训练时的白纸垫位置**，验证"能不能复现训练场景"。
这一步成功了，才说明链路是通的；位置一变就失败，那是数据问题，不是部署问题。
